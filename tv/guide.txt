Build a production-ready MVP web application called **Centryk TV**.

Centryk TV is part of the broader **Centryk business application suite**. It is a multi-tenant live-streaming and digital broadcasting platform for businesses, schools, sports organizations, churches, government agencies, event organizers, and other organizations.

The goal is **not** to clone YouTube. Centryk TV should focus on controlled, branded, organization-owned streaming experiences including live sports, graduations, conferences, training sessions, ceremonies, public events, private broadcasts, and eventually pay-per-view and subscription content.

The platform should separate the **business application/UI layer** from the **video streaming infrastructure**.

## Core Architecture

Use this architecture:

```text
GoDaddy DNS
│
├── tv.example.com
│       ↓
│   Cloudways
│   Centryk TV Web Application
│
└── stream.example.com
        ↓
    IONOS VPS
    Streaming Infrastructure
```

The Cloudways application must handle:

* UI
* authentication
* users
* organizations
* roles and permissions
* channels
* events
* stream credentials
* viewer authorization
* schedules
* replay metadata
* analytics
* settings
* future billing integration

The IONOS VPS will eventually handle:

* RTMP ingest
* HLS output
* NGINX or SRS
* FFmpeg where necessary
* streaming bandwidth
* stream status
* stream-key validation
* signed/tokenized playback

For this initial build, create a clean abstraction/interface for the streaming server so the Cloudways application can function before the actual IONOS server is configured.

Do not tightly couple the application to a specific streaming engine.

# Playback Security

Do not make permanent public `.m3u8` links the core security model.

Design the application for signed/tokenized playback.

Expected future flow:

```text
Viewer requests /watch/event

Centryk verifies:

user
organization
event
visibility
access rights

↓

Centryk generates temporary playback token

↓

Player receives temporary stream URL

↓

IONOS streaming server validates token

↓

HLS plays
```

For MVP:

Implement the token-generation side in PHP.

Use:

* HMAC SHA-256
* expiration timestamp
* event or stream identifier
* secret from `.env`

Example conceptual URL:

```text
https://stream.example.com/hls/channel.m3u8
?expires=...
&token=...
```

Create functions cleanly so the eventual NGINX/SRS validation implementation can match it.

Do not expose the signing secret client-side.

# Build Process

Work iteratively.

Before writing large amounts of code:

1. Inspect the existing repository.
2. Understand the existing architecture.
3. Preserve useful existing code and conventions.
4. Produce a short implementation plan.
5. Build Phase 1 first.
6. Run and test it.
7. Fix errors before proceeding.
8. Continue phase-by-phase.

Do not rewrite an existing working codebase unnecessarily.

When modifying files, make the actual changes rather than only describing what should change.

Run available tests, linting, syntax checks, and database validation after significant changes.

        ↓

        ↓
